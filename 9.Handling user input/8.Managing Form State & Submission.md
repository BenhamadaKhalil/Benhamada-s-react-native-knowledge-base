# 🎬 Handling Form Submission in React Native (Expense Form Architecture)

## 🧠 Core Concept
In this step, we refactor responsibility so that:

- 🧾 `ExpenseForm` → handles form state + submission
- 🖥️ `ManageExpense` → handles screen-level actions (open/close modal, navigation)
- 🔘 Buttons move into the form (where they logically belong)

👉 This is about **clean architecture and responsibility separation**

---

## 🧱 1. Moving Buttons into ExpenseForm

### 📌 What changes?

We move:

- Confirm Button
- Cancel Button
- Button styles

from `ManageExpense` → `ExpenseForm`

---

### 🧠 Why this is better

Because:

- The form owns the inputs
- The form should also own submission
- Keeps screen component clean

---

## 🧩 4. Adding Form Layout for Buttons

```jsx
<View style={styles.buttons}>
  <Button title="Cancel" onPress={onCancel} />
  <Button title={submitButtonLabel} onPress={submitHandler} />
</View>
```

---

## 🔁 5. Handling Cancel Action

### 📌 Key Idea

Cancel does NOT belong to the form logic.

It belongs to the **screen (ManageExpense)**.

---

### 📦 Prop passed into form:

```js
<ExpenseForm onCancel={cancelHandler} />
```

---

### 📦 Inside ExpenseForm:

```js
<Button title="Cancel" onPress={onCancel} />
```

---

### 🧠 Why?

Cancel means:

- Close modal
    
- Navigate back
    
- Screen-level behavior
    

👉 Not form-related logic

---

## 🚀 6. Handling Submit Action

### 📌 Inside ExpenseForm

We create:

```js
const submitHandler = () => {
  // will process form data
};
```

---

### 📦 Passed as prop:

```js
<ExpenseForm onSubmit={submitHandler} />
```

---

### 📦 Connected to button:

```js
<Button title={submitButtonLabel} onPress={submitHandler} />
```

---

## 🧠 Key Architecture Decision

|Action|Belongs to|
|---|---|
|Cancel|ManageExpense (screen)|
|Submit|ExpenseForm (form)|

---

## 🧩 7. Passing Dynamic Button Label

We support Add vs Update mode:

### 📦 In ManageExpense:

```js
submitButtonLabel={isEditing ? 'Update' : 'Add'}
```

---

### 📦 In ExpenseForm:

```js
<Button title={submitButtonLabel} />
```

---

### 🧠 Why this matters

- Keeps form reusable
    
- Screen decides context (add/edit)
    
- Form stays generic
    

---

## 🧠 8. Optional Alternative (Mentioned in Lecture)

We could also pass:

- `isEditing` directly into form
    
- and decide label inside form
    

👉 But instructor prefers:

- Screen controls business logic
    
- Form stays presentation-focused
    

---

## 🔁 Final Architecture Flow

```text
ManageExpense (Screen)
   ↓ passes props
ExpenseForm (Form logic)
   ↓ handles input + submit
Input components (UI fields)
   ↓
TextInput (native input)
```

---

## ⚙️ Mental Model

Think of it like this:

- 🖥️ Screen = orchestration layer
    
- 🧾 Form = business input logic
    
- 🧩 Input = reusable UI component
    
- 🔘 Button = triggers actions
    

👉 Clean separation = scalable app

---

## 🚨 Common Mistakes

- ❌ Keeping form submission in screen instead of form
    
- ❌ Mixing cancel + submit logic in same place
    
- ❌ Hardcoding button labels inside form
    
- ❌ Not passing handlers via props
    
- ❌ Losing separation between UI and logic
    

---

## 🧪 Takeaways

- Move buttons into the form (logical grouping)
    
- Cancel → screen responsibility
    
- Submit → form responsibility
    
- Use props to connect actions
    
- Keep form reusable across Add/Edit modes
    

---

## ⚡ Quick Summary

- Moved buttons into `ExpenseForm`
    
- Added `submitHandler` inside form
    
- Kept `cancelHandler` in screen
    
- Passed `onCancel`, `onSubmit`, `submitButtonLabel`
    
- Improved separation of concerns
    
- Built cleaner, scalable form architecture
